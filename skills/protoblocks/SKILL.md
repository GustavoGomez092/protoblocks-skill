# Proto-Blocks

## Overview

Proto-Blocks is a WordPress plugin for building Gutenberg blocks with **PHP/HTML templates instead of React**. A block is a folder containing a `block.json` (with a `protoBlocks` config) and a `template.php`. The same PHP template renders both the editor preview and the frontend. Editable regions are marked with `data-proto-*` HTML attributes — the plugin wires those to editor UI automatically.

**Requirements:** WordPress 6.3+, PHP 8.0+. Current plugin version: 2.14.0

**Core mental model:**
- `block.json` → declares `fields` (editable content) and `controls` (inspector settings) under a `protoBlocks` key.
- `template.php` → plain PHP/HTML. Reads values from `$attributes`. Marks editable elements with `data-proto-field`, repeaters with `data-proto-repeater`.
- Fields and controls both become block attributes, readable as `$attributes['name']`.

**Design principle — model the fewest, richest regions.** Don't chop one authored area into many fields. A region of "heading + paragraph + list" is **one wysiwyg field** (or an inner-blocks slot), not three fields. Discrete fields are for distinct, individually-placed/styled slots. See `references/composition.md` before designing a block.

## When to Use

- Creating a new Proto-Blocks block (scaffold `block.json` + `template.php`).
- Adding fields (text, image, video, link, wysiwyg, repeater, inner-blocks) or controls (select, toggle, range, color, image/video picker, etc.), including conditional controls.
- Debugging: block not appearing, preview not updating, field not editable, repeater issues, Tailwind not applying.
- Writing `template.php` markup with correct `data-proto-*` bindings and escaping.
- Declaring post types, taxonomies, field groups or settings pages, or reading their values → "Content model" below.
- Building whole pages or a site from a design → use `protoblocks-site-builder`.

**Not for:** classic React/`@wordpress/scripts` block development, or non-Proto-Blocks WordPress work.

## Anatomy of a Block

```
your-theme/proto-blocks/my-block/   ← discovered automatically (theme's proto-blocks/ dir)
├── block.json        REQUIRED — standard block metadata + a "protoBlocks" key
├── template.php      REQUIRED — PHP/HTML, renders preview AND frontend
├── style.css         optional — block styles (or {block-name}.css)
├── view.js           optional — frontend JS (or Interactivity API ES module)
└── preview.png       optional — inserter thumbnail (auto-generated by Preview Capture)
```

The **folder name is the block slug**. Default block name is `proto-blocks/{folder}`. Discovery scans the active theme's `proto-blocks/` directory (and child theme); add more paths via the `proto_blocks_paths` filter.

`"category"` defaults to `proto-blocks`. On a site built with `protoblocks-site-builder`, setup registers one inserter category per site (slug = the theme slug, `site.theme.category.slug` in the build state): every `block.json` on that site must use that slug, not `proto-blocks`.

## Minimal Block

`block.json`:
```json
{
  "$schema": "https://schemas.wp.org/trunk/block.json",
  "apiVersion": 3,
  "name": "proto-blocks/callout",
  "title": "Callout",
  "category": "proto-blocks",
  "icon": "megaphone",
  "supports": { "html": false, "anchor": true },
  "protoBlocks": {
    "version": "1.0",
    "template": "template.php",
    "useTailwind": false,
    "fields": {
      "heading": { "type": "text", "tagName": "h3" },
      "body": { "type": "wysiwyg" }
    },
    "controls": {
      "tone": {
        "type": "select",
        "label": "Tone",
        "default": "info",
        "options": [
          { "key": "info", "label": "Info" },
          { "key": "warning", "label": "Warning" }
        ]
      }
    }
  }
}
```

`template.php`:
```php
<?php
$heading = $attributes['heading'] ?? '';
$body    = $attributes['body'] ?? '';
$tone    = $attributes['tone'] ?? 'info';
?>
<div <?php echo get_block_wrapper_attributes(['class' => 'callout callout--' . esc_attr($tone)]); ?>>
    <h3 data-proto-field="heading"><?php echo esc_html($heading); ?></h3>
    <div data-proto-field="body"><?php echo wp_kses_post($body); ?></div>
</div>
```

That's a complete, editable block. `heading`/`body` are editable inline in the editor; `tone` appears as a dropdown in the inspector sidebar.

## Quick Reference

### Field types (`protoBlocks.fields`)
| Type | Attribute value shape | Bind with |
|------|----------------------|-----------|
| `text` | string | `data-proto-field` |
| `wysiwyg` | string (HTML) | `data-proto-field` |
| `image` | `{ id, url, alt, caption, size }` | `data-proto-field` |
| `video` | `{ id, url, mime }` | `data-proto-field` (media-library video; also a control) |
| `link` | `{ url, text, target, rel, title }` | `data-proto-field` |
| `repeater` | array of `{ id, ...fields }` | `data-proto-repeater` + `data-proto-repeater-item`; sub-values the template consumes go in `itemControls` (sidebar, per row) rather than `fields` |
| `inner-blocks` | nested blocks → `$innerBlocksContent` | `data-proto-inner-blocks` (one per block; type must be hyphenated) |

### Control types (`protoBlocks.controls`)
`text`, `textarea`, `select`, `multiselect`, `toggle`, `checkbox`, `range`, `number`, `color`, `color-palette`, `radio`, `image`, `video`, `gallery`, `file`, `repeater`. Select/radio need `options` (or, for `select`/`multiselect`, a server-loaded `optionsSource`); range needs `min`/`max`; `multiselect` stores an ordered array of keys. Any control can declare `conditions.visible`. `image`/`video` exist as both fields and controls (control = sidebar media picker); `file` is the picker for anything else, read by attachment id. A `repeater` control holds repeated configuration (tabs, breakpoints, a pasted CSV) where a repeater field holds repeated content; a value the template parses rather than prints belongs in a control or in the field's per-row `itemControls` (Iron Rule 3b). `gallery` is the multi-image control: use it instead of a repeater of images whenever the images are the layout. Details: `references/controls.md`, `references/repeaters.md`.

### `data-proto-*` attributes
| Attribute | Purpose |
|-----------|---------|
| `data-proto-field="name"` | Bind element to a field |
| `data-proto-repeater="name"` | Repeater container |
| `data-proto-repeater-item` | One per repeated item |
| `data-proto-inner-blocks` | Inner blocks slot (alt to a field) |

### Template variables
| Variable | Notes |
|----------|-------|
| `$attributes` | All field + control + core values. Hyphenated keys become underscored. |
| `$block` | `WP_Block` on frontend, **`null` in editor preview** — check it to detect preview |
| `$innerBlocksContent` | Nested-blocks HTML for an `inner-blocks` field. **Echo this, not `$content`** (`$content` is not passed). Always `?? ''`. |
| `$template` | Helper: `$template->has_value($name)`, `$template->get($name, $default)` |

### WP-CLI
```bash
wp proto-blocks list [--format=table|json]
wp proto-blocks create <name> --title="..." --fields="title:text,img:image"
wp proto-blocks validate [<name>]
wp proto-blocks cache clear
wp proto-blocks cache stats
wp proto-blocks export <name> --output=<path>
```

## Content model (plugin 2.15.0+)

Post types, taxonomies, custom fields and settings pages are theme files (the admin UI edits the same files):

```
proto-types/<slug>/type.jsonc     post type (+ inline taxonomies, field groups)
proto-taxonomies/<slug>/taxonomy.jsonc
proto-fields/<slug>/group.jsonc   field group, ACF local-JSON shape
proto-options/<slug>/page.jsonc   settings page
```

PHP one-liners (functions.php): `proto_post_type('Event')`, `proto_taxonomy('Topic', ['post_types' => ['event']])`, `proto_field_group('event', [...])`, `proto_options_page('Theme Settings', [...])`. Read values escaped per type: `proto_field('subtitle')`, `proto_rows('agenda')`, `proto_field('phone', 'option:theme-settings')`, `$template->field('subtitle')` in `template.php`; core blocks: Block Bindings source `proto-blocks/field`.

Decide: per-instance section copy → block field. Same data wherever a post shows (date, venue, role) → custom field. A collection with its own URLs → post type. Site-wide values (phone, footer, scripts) → settings page.

Rules: prefer files over PHP (file wins, "declared twice" warning); folder = slug; child theme wins; files cannot name PHP callbacks; no `<`/`>` in labels; `code`/`password` values need `unfiltered_html` (CLI seeding: `--user=<admin>`); no read-permission check, never pass visitor input as context; never rename a slug with content by hand. After every change: `wp proto-blocks validate`.

## Iron Rules (cause most bugs when ignored)

1. **Always escape output**: `esc_html()`, `esc_attr()`, `esc_url()`, `wp_kses_post()` (for wysiwyg/HTML).
2. **Always provide defaults**: `$attributes['x'] ?? ''` — attributes can be missing.
3. **Mark editable elements even when empty.** A field is only editable in the editor if its element carries `data-proto-field`. Render the element (with the attribute) even when the value is empty, or it can't be edited.
3b. **Every declared field must be bound somewhere — including the ones you never print.** A field the template *consumes* rather than displays (a CSV parsed into a table, a colour fed to a `style` attribute, a key that picks an icon) has no element in the front-end markup, so nothing will ever be its input: the block renders perfectly and cannot be authored. Where it goes depends on where it lives:
    - **Inside a repeater row** → declare it in the repeater's **`itemControls`** (2.13.0+), not its `fields`. It is then edited in the sidebar whenever that row is focused. See `references/repeaters.md`.
    - **At block level** → declare it as a **control**, not a field (a `repeater` control for repeated configuration, any other control for a single value).
    - **Only if neither fits** → an editor-only authoring region behind `$is_preview`. This is the last resort: it puts editing furniture into the block's own markup.

    `references/authoring-workflow.md` has a check that lists unbound fields. **Run it before the gates, every time.**
4. **`data-proto-repeater` name must match the repeater field name** in `block.json`.
5. **Inner blocks:** type must be hyphenated **`"inner-blocks"`** (plain `innerblocks` is silently skipped), bind with **`data-proto-inner-blocks`**, echo **`$innerBlocksContent ?? ''`** (not `$content`), and only **one per block**.
6. **`select` and `multiselect` controls must define `options`** (use `{ "key", "label" }` pairs) **or** an `optionsSource` (server-loaded options — see `references/controls.md`). Either type with neither fails validation.
7. **Clear the cache after template changes** if you don't see updates: `wp proto-blocks cache clear`. Parsed templates are cached (validated against template + `block.json` mtime); an object cache or OPcache layer can still serve stale output, so clear explicitly when in doubt.
