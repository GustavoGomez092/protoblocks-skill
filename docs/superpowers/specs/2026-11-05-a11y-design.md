# Accessibility verification (2.6.0) — spec

The developer's request, verbatim, 2026-11-05. The interface contract that implements it: `docs/superpowers/plans/2026-11-05-a11y-interfaces.md`.

## Context

Page QA (skills/protoblocks-site-builder/scripts/qa/page-qa.mjs) already runs axe through @axe-core/playwright: tags wcag2a, wcag2aa, wcag21a, wcag21aa; one pass at the first design frame's width, right after load; violations scoped to main/header/footer/#pb-s… (filterViolations); only serious/critical block the page, minor/moderate land in `a11y.other` and the final report. Docs: skills/protoblocks-site-builder/references/pipeline.md (page-qa section and Recovery), SKILL.md final report item 5.

A client WCAG scan of a finished site (oflex.com, built with this skill) found issues that this setup let through, every one reproducible with axe:
- `landmark-unique` (best-practice): the site-header block wrapped the core navigation block in a second <nav aria-label="Primary"> — nav inside nav.
- Five small navigation landmarks: three footer core/navigation blocks (2–5 links each) plus the nested pair; the scan's rule was "navigation landmark does not contain key site navigation links".
- `heading-order` (best-practice): footer column titles were h3 under pages whose last heading was h1; contact location names h3 between h1 and h2.
- `target-size` (wcag22aa, serious): logo-carousel slide dots were 8px buttons.
- A tabs block built with aria-owns (tab buttons outside the tablist, panels interleaved) passed axe's wcag tags but failed the scan's tabpanel rule.
- Dropdown parents rendered as <a> without href (no role, not a button).
- aria-current="page" never set on the header/footer logo links, and stale after Taxi page swaps because the header persists; a footer "#cookie-settings" hash link counted as current page.
- role="img" on a <div> wrapping an SVG instead of on the SVG.

## What to build

1. page-qa.mjs axe pass
   - Tags: add `wcag22a`, `wcag22aa` and `best-practice`. Keep the existing scoping.
   - Blocking: serious + critical as today, plus these moderate rules: `landmark-unique`, `landmark-no-duplicate-main`, `landmark-main-is-top-level`, `heading-order`, `region` (except nodes that are WordPress core's `#wp-skip-link`, which is always reported as info, never blocking). Make the blocking list a named constant with a comment per rule, and let `site.qa.a11yBlocking` in state override it (array of rule ids), documented in references/state-schema.md.
   - Run axe at every design frame width that page QA already screenshots (desktop and the narrowest mobile frame at minimum), not only frames[0].width, and merge results by rule id + target. Mobile exposes the responsive menu, overlay dialogs and target-size failures.
   - Add a "post-navigation" pass: from the page under test, click the first same-site header link that is not the current page, wait for `proto:page-ready` (see the theme's scripts/proto-taxi.js in proto-blocks-theme; fall back to a load event when Taxi is absent), run axe again, and also assert aria-current="page" is on exactly the header/footer links whose pathname equals the new location and on no hash-only link. Report as `a11y.afterNavigation`. Skip with a warning (not a failure) when the theme has no Taxi.
   - Custom widget checks, run in the same page.evaluate and reported under `a11y.patterns` as blocking:
     * every [role=tab] is a child (or aria-owns-free descendant) of a [role=tablist]; every [role=tabpanel] has aria-labelledby pointing at a [role=tab]; no [role=tabpanel] sits between tabs inside the tablist;
     * no <a> without href unless it has role="button" and tabindex="0";
     * role="img" only on <svg>, <img>, <canvas>, or an element with no child elements and an accessible name;
     * at most one <main>; no <nav> inside <nav>; a <nav> with fewer than 2 links (counted per landmark; a wrapper with role=group inside a nav is fine);
     * heading sequence never skips a level across the whole document (including header/footer parts), reported with the two headings involved.
   - Output: keep `a11y: {blocking, other}` and add `a11y.byViewport`, `a11y.afterNavigation`, `a11y.patterns`, `a11y.tagsUsed`. Each violation keeps axe's `id`, `impact`, `help`, `helpUrl`, and up to 5 node targets with a 120-char html snippet. `page-qa.mjs record` must refuse `--accepted` when any blocking a11y item remains (today it already refuses on blocking violations; extend to `patterns` and `afterNavigation`).

2. Site-wide pass before launch
   - New `scripts/qa/site-a11y.mjs run <themeDir> [--out file]`: iterates every page in state with a url (plus the 404 page: `<home>/__pb-404-probe__`), runs the same axe routine (shared module, no duplication: extract the axe code from page-qa.mjs into scripts/qa/a11y.mjs and import it from both), and prints `{pages: [{slug, url, blocking, other, patterns, afterNavigation}], pass}`; exit 1 unless pass. Save to `$THEME/.protoblocks/artifacts/site-a11y.json`.
   - Wire it into the site-builder flow: in SKILL.md and references/pipeline.md, run it as the first step of `ask-more-pages` when the developer says there are no more pages, before the final report; a failing site pass is fixed through the section loop like any other page-QA content failure (document that, do not duplicate the section-loop steps). The final report (SKILL.md item 5) lists remaining `other` items per page and says the site pass passed.

3. Authoring guidance so blocks stop producing these
   - skills/protoblocks/references/templates.md: a short "Accessibility conventions" section: one landmark per role per region (never wrap a core/navigation block in a nav; header/footer blocks use div wrappers and let core render the nav); footer menus in one <nav aria-label="Footer"> with inner core navs demoted via a render_block_core/navigation filter (point to the pattern, give the 15-line PHP); heading levels per region; tabs = ARIA tabs pattern on the frontend, tab+panel rows only under $is_preview; role=img on the SVG itself; no href-less anchors (link the parent or render a <button>); touch targets ≥ 24px with a pseudo-element for small visual dots; aria-current handled by the theme (link to proto-taxi.js syncNavState).
   - skills/protoblocks/references/recipes.md tabs recipe and the section-loop verify step: add "run the pattern checks" (section-loop can call `node scripts/qa/a11y.mjs check-section <url> <anchor>` which runs axe scoped to one section anchor — add that subcommand too, so a11y failures surface per section before page QA).

4. Tests and docs
   - Unit tests (tests/unit, node --test): filterViolations with the new blocking list and the site.qa override; the pattern checks against small HTML fixtures (nested nav, aria-owns tabs, href-less anchor, div role=img, heading skip, hash link aria-current) — run them with Playwright against `data:` or file:// fixtures as the existing qa tests do.
   - Update references/pipeline.md (page-qa output shape, record rules, site pass), references/state-schema.md (`site.qa.a11yBlocking`), SKILL.md (ask-more-pages step, final report), CHANGELOG.md, and bump the plugin version (minor: 2.6.0) in .claude-plugin/plugin.json and wherever the version is echoed (grep for 2.5.0).
   - Keep `npm test` green and run the integration/e2e suite that covers page-qa if it exists in tests/.

## Acceptance

- Re-running page QA on a page whose header contains a nav-in-nav, a footer with three small navs, an 8px dot button, and a tabs block built with aria-owns fails with those items listed as blocking, each with rule id, help URL and node snippet.
- After the fixes (div wrapper, one footer nav with grouped inner navs, 24px dots, tablist-contained tabs) the same page passes, and the only `other` item is `region` on #wp-skip-link, reported as info.
- The post-navigation pass fails when aria-current is stale after a Taxi swap and passes once the theme syncs it.
- site-a11y.mjs runs across a built site and the docs tell the agent exactly when to run it.
